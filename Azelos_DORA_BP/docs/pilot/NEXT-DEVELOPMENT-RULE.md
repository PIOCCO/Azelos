# Next development rule (after first pilot)

**Do not automatically build requested features.**

A capability becomes a **serious candidate** for the next iteration only when there is evidence such as:

- **Repeated occurrence** across customers or ≥2 distinct users in one pilot
- **Significant manual work** remaining outside the BP for a core workflow
- **Direct blockage** of a core workflow (pilot blocker, not preference)
- **Clear operational value** described with concrete examples (meetings, reports, audits)
- **Willingness to use or pay** for that specific capability (customer-initiated)

## Keep separate

- **Customer-specific requests** — track but do not merge into roadmap without broader evidence
- **Nice-to-have / out of scope** — defer per [PILOT-BOUNDARY.md](./PILOT-BOUNDARY.md)

## Classify every request

Use labels in [WEEKLY-REVIEW-TEMPLATE.md](./WEEKLY-REVIEW-TEMPLATE.md): pilot blocker, repeated workflow problem, customer-specific, nice-to-have, out of scope.

## Known post-pilot candidates (from readiness audit—not commitments)

Only if customer evidence confirms pain:

- UI to link evidence to requirements
- UI for tenant export
- Formatted (non-JSON) reports
- OIDC SSO as default login path

No work starts without evidence from the first real pilot.
